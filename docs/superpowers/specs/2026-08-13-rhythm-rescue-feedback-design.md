# 《리듬 구조대》 피드백·오디오 설계서

작성일: 2026-08-13
상태: 승인된 구현 설계
기준 브랜치: `codex/mission-progression`
대상: 초등 5~6학년 중심의 1인 브라우저 플레이어

## 1. 목표와 범위

다중 수리 지점 임무에서 입력 결과를 즉시 이해할 수 있도록 성공, 실수, 복구, 지점 완료, 임무 완료를 시각·청각·촉각 피드백으로 구분한다. 소리와 진동을 꺼도 문구, 아이콘, 진행도만으로 임무를 끝까지 플레이할 수 있어야 한다.

이번 사이클은 외부 음원 파일이나 별도 에셋 없이 브라우저 Web Audio API로 짧은 신호음을 생성한다. 오디오·진동 API가 없거나 초기화에 실패해도 판정, 장면 전환, 보상 저장은 계속 동작한다.

## 2. 선택한 접근

| 접근 | 장점 | 단점 | 결정 |
| --- | --- | --- | --- |
| Web Audio 합성음 | 외부 에셋 없음, 로딩이 빠름, 이벤트별 음높이 제어 가능 | 음악적 풍부함이 제한됨 | **채택** |
| 로컬 효과음 파일 | 완성도 높은 음색 가능 | 파일 관리·로딩·라이선스 부담 | 후속 작업 |
| CSS와 시스템 피드백만 사용 | 구현이 단순함 | 소리 피드백과 이벤트 구분이 약함 | 미채택 |

피드백 이벤트와 브라우저 효과를 분리한다. 게임 판정은 이벤트를 발행하고, 효과 계층은 설정과 브라우저 지원 여부를 확인한 뒤 소리·진동을 실행한다. 따라서 효과 구현을 교체해도 `MissionRunState`의 판정 규칙은 변하지 않는다.

## 3. 이벤트 계약

피드백 이벤트는 다음 다섯 가지로 제한한다.

| 이벤트 | 발생 시점 | 시각 피드백 | 소리 | 진동 |
| --- | --- | --- | --- | --- |
| `input-correct` | 현재 패턴과 입력이 일치할 때 | 입력 진행도와 콤보 갱신 | 짧은 높은음 | 짧은 1회 |
| `input-wrong` | 패턴과 다른 입력을 했을 때 | 오류 문구와 실수 수 갱신 | 짧은 낮은음 | 짧은 강한 1회 |
| `recovery-used` | 복구 신호를 사용했을 때 | 복구 안내와 재입력 상태 | 중간음 2회 | 짧은 2회 |
| `point-complete` | 수리 지점 하나를 완료했을 때 | 다음 지점 미리보기와 지점 수 갱신 | 상승 2음 | 짧은 2회 |
| `mission-complete` | 마지막 수리 지점을 완료했을 때 | 결과 화면으로 전환 | 짧은 완료 화음 | 완료 패턴 |

예상 타입은 다음과 같다.

```ts
export type FeedbackEvent =
  | 'input-correct'
  | 'input-wrong'
  | 'recovery-used'
  | 'point-complete'
  | 'mission-complete';

export interface FeedbackBus {
  emit(event: FeedbackEvent): void;
  subscribe(listener: (event: FeedbackEvent) => void): () => void;
}
```

`subscribe`는 해제 함수를 반환한다. 씬이 종료될 때 구독을 해제해 이전 임무의 효과가 남지 않게 한다.

## 4. 구성 요소와 데이터 흐름

### 4.1 `FeedbackBus`

`src/core/feedback.ts`에 브라우저 API를 모르는 동기 이벤트 버스를 둔다. 이벤트 순서를 보존하고, 리스너가 하나 실패해도 다른 리스너와 게임 판정에 영향을 주지 않도록 각 리스너 호출을 격리한다.

### 4.2 `FeedbackEffects`

`src/feedback/feedback-effects.ts`에 오디오·진동 효과를 둔다.

- `sound === false`이면 `AudioContext`를 생성하거나 oscillator를 만들지 않는다.
- `vibration === false`이거나 `navigator.vibrate`가 없으면 진동을 건너뛴다.
- 사용자 입력 이후 오디오 컨텍스트를 지연 생성하고, `resume()` 실패는 무시한다.
- 이벤트별 주파수·길이·진동 패턴은 상수로 관리한다.
- `dispose()`에서 오디오 컨텍스트를 닫고 이벤트 구독을 해제한다.
- 모든 브라우저 API 호출은 `try/catch` 경계 안에 두며 예외를 게임 코드로 전파하지 않는다.

### 4.3 `MissionScene` 연결

임무 씬은 `create`에서 현재 `Progress.settings`로 버스를 만들고 효과 리스너를 연결한다. 입력 흐름은 다음 순서로 유지한다.

```text
입력
→ MissionRunState 판정
→ FeedbackBus 이벤트 발행
→ 시각 상태 render
→ 설정이 허용하면 소리·진동
```

- 정상 입력: `input-correct`
- 오입력: `input-wrong`
- 오입력 직후 복구 적용: `recovery-used`
- `completedPoints` 증가: `point-complete`
- 마지막 지점 완료 직전 결과 전환: `mission-complete`

판정 결과가 먼저 확정되고 이벤트가 뒤따른다. 효과 실행이 늦거나 실패해도 `ResultScene` 전환과 보상 저장은 영향을 받지 않는다.

### 4.4 시각 피드백과 접근성

현재 임무 문구와 진행 카드를 재사용하되 이벤트별 상태를 추가한다.

- 성공: 콤보·입력 진행도와 짧은 성공 문구를 갱신한다.
- 실수: 실수 수와 복구 안내를 표시한다.
- 복구: 다시 입력할 패턴임을 명시한다.
- 지점 완료: 다음 지점 번호와 미리보기 상태를 표시한다.
- 임무 완료: 결과 화면에 도달한다.

색상만으로 상태를 전달하지 않는다. 오류·복구·완료는 문구와 진행 수치로도 식별 가능하게 한다. 반복 성공 입력은 화면 낭독기가 과도하게 읽지 않도록 별도 `aria-live` 알림을 만들지 않고, 실수·복구·완료 상태만 polite 알림으로 전달한다.

## 5. 설정과 저장

기존 `Progress.settings.sound`와 `Progress.settings.vibration`을 그대로 사용한다. 저장 형식을 변경하거나 새 설정 키를 추가하지 않는다.

본부에서 설정을 끄고 임무를 시작하면 해당 임무의 효과 계층이 즉시 비활성화된다. 설정이 꺼져도 입력 버튼, 문구, 패턴 카드, 결과 보상은 동일하게 동작한다.

## 6. 테스트 전략

### 단위 테스트

- 이벤트 버스가 구독 순서대로 이벤트를 전달한다.
- 반환된 해제 함수 이후에는 이벤트를 받지 않는다.
- `sound: false`일 때 Web Audio 객체를 만들지 않는다.
- `vibration: false` 또는 미지원 브라우저에서 진동을 호출하지 않는다.
- Web Audio와 진동 API가 예외를 던져도 효과 함수가 예외를 전파하지 않는다.

### E2E 테스트

- 튜토리얼에서 오입력 시 오류·복구 문구가 표시되고, 올바른 입력으로 임무를 완료한다.
- 소리와 진동을 끈 상태에서도 튜토리얼과 결과 화면이 정상 동작한다.
- 기존 키보드·마우스·좁은 화면·일시정지 시나리오가 유지된다.

## 7. 비목표와 후속 작업

- 배경 음악, 볼륨 믹서, 음원 파일 다운로드는 포함하지 않는다.
- Web Audio 효과를 악기 음색이나 멜로디로 확장하지 않는다.
- 스킨·기지 장식·해금 조건은 별도 사이클에서 구현한다.
- 장시간 플레이테스트와 실제 모바일 브라우저별 음량 튜닝은 후속 검증으로 남긴다.

## 8. 완료 기준

- 각 이벤트가 지정된 판정 지점에서 정의된 횟수와 순서로 발행된다.
- 설정과 브라우저 지원 여부에 따라 소리·진동이 안전하게 켜지고 꺼진다.
- 효과 API 실패가 게임 결과에 영향을 주지 않는다.
- 소리·진동을 끈 E2E에서도 임무 완료와 보상 저장이 통과한다.
- 기존 단위 테스트, E2E, 프로덕션 빌드가 모두 통과한다.
